# check_bottleneck.sh 스크립트 체크 항목 설명

## 체크 1: 서비스 상태

### 제목
서비스 상태 (Health Check)

### 목적
Spring Boot 서비스의 기본 상태를 확인하여 서비스가 정상 작동 중인지, 또는 장애 상태인지 판단합니다. DB, Redis, Mail 등 모든 컴포넌트의 상태를 포함합니다.

### 계산
Spring Actuator의 `/actuator/health` 엔드포인트를 호출하여 응답을 받습니다. 응답 JSON에서 "UP" 문자열이 포함되어 있는지 확인합니다.

### 판단
- 응답에 "UP"이 포함되어 있으면 → 정상 작동 중
- 응답에 "UP"이 없거나 "DOWN"이 포함되어 있으면 → 서비스 DOWN 상태
- Health 체크 자체가 실패하면 → 서비스가 실행 중이지 않을 수 있음

### 의미
서비스가 정상적으로 시작되었고, 모든 의존성(데이터베이스, Redis, 메일 서버 등)에 정상적으로 연결되어 있는지 확인합니다. 이 체크가 실패하면 다른 모든 체크가 의미 없을 수 있습니다.

## 체크 2: 응답 시간 체크

### 제목
응답 시간 체크 (Response Time Metrics)

### 목적
API 엔드포인트의 응답 시간을 측정하여 서비스가 느려지고 있는지, 즉 병목 현상이 발생하고 있는지 확인합니다.

### 계산
Actuator 메트릭 엔드포인트에서 `/api/auth/login` 엔드포인트의 총 응답 시간(TOTAL_TIME)과 요청 수(COUNT)를 가져옵니다.
평균 응답 시간 = 총 응답 시간 / 요청 수

### 판단
- 평균 응답 시간이 1.2초를 초과하면 → 경고
- 평균 응답 시간이 1.2초 이하면 → 정상
- 요청 수가 0이거나 데이터가 없으면 → 데이터 없음

### 의미
응답 시간이 급증하면 사용자 경험이 나빠지고, 서비스 내부에서 병목이 발생하고 있을 가능성이 높습니다. 특히 평소보다 3배 이상 느려지면 심각한 병목 현상으로 판단할 수 있습니다.

## 체크 3: 데이터베이스 연결 풀 체크

### 제목
데이터베이스 연결 풀 체크 (Database Connection Pool)

### 목적
HikariCP 연결 풀의 사용률을 확인하여 데이터베이스 연결이 포화 상태인지 확인합니다. 연결 풀 포화는 데이터베이스 병목의 주요 원인입니다.

### 계산
Actuator 메트릭에서 다음 세 가지 값을 가져옵니다:
- 활성 연결 수 (hikaricp.connections.active)
- 최대 연결 수 (hikaricp.connections.max)
- 대기 중인 연결 요청 수 (hikaricp.connections.pending)

연결 풀 사용률 = (활성 연결 수 / 최대 연결 수) × 100

### 판단
- 연결 풀 사용률이 90%를 초과하면 → 심각 (연결 풀 포화)
- 대기 중인 연결 요청(pending)이 0보다 크면 → 경고 (요청이 대기 중)
- 연결 풀 사용률이 90% 이하이고 pending이 0이면 → 정상

### 의미
데이터베이스 연결 풀이 포화되면 새로운 요청이 연결을 얻기 위해 대기해야 하므로 응답 시간이 급증합니다. 이는 데이터베이스 쿼리가 느리거나, 연결 풀 크기가 부족하거나, 연결이 제대로 반환되지 않는 경우에 발생합니다.

## 체크 4: Circuit Breaker 상태

### 제목
Circuit Breaker 상태 (Resilience4j Circuit Breaker)

### 목적
Resilience4j Circuit Breaker의 상태를 확인하여 하위 서비스와의 통신이 정상인지, 또는 하위 서비스에 장애가 발생하여 차단되었는지 확인합니다.

### 계산
Actuator 메트릭에서 `resilience4j.circuitbreaker.state` 값을 가져옵니다. 값이 0이면 CLOSED, 1이면 OPEN 상태입니다.

### 판단
- Circuit Breaker 상태가 1 (OPEN)이면 → 심각 (하위 서비스 장애 가능)
- Circuit Breaker 상태가 0 (CLOSED)이면 → 정상 (하위 서비스 통신 정상)
- 메트릭 데이터를 가져올 수 없으면 → jq 없이 로그에서 간단히 확인

### 의미
Circuit Breaker가 OPEN 상태라는 것은 하위 서비스(예: Auth → User 서비스)에서 실패율이 임계값을 초과했다는 의미입니다. 이 상태에서는 하위 서비스로의 요청이 즉시 차단되어 실패 응답을 반환합니다. 이는 하위 서비스에 장애가 발생했거나, 네트워크 문제가 있거나, 하위 서비스가 과부하 상태일 수 있습니다.

## 체크 5: 힙 메모리 사용률

### 제목
힙 메모리 사용률 (JVM Heap Memory Usage)

### 목적
JVM 힙 메모리의 사용률을 확인하여 메모리 부족으로 인한 성능 저하나 OutOfMemoryError 발생 가능성을 확인합니다.

### 계산
Actuator 메트릭에서 다음 두 값을 가져옵니다:
- 사용 중인 힙 메모리 (jvm.memory.used, area=heap, bytes 단위)
- 최대 힙 메모리 (jvm.memory.max, area=heap, bytes 단위)

힙 메모리 사용률 = (사용 중인 힙 메모리 / 최대 힙 메모리) × 100
사용 중인 힙 메모리 (MB) = 사용 중인 힙 메모리 (bytes) / 1024 / 1024
최대 힙 메모리 (MB) = 최대 힙 메모리 (bytes) / 1024 / 1024

### 판단
- 힙 메모리 사용률이 85%를 초과하면 → 경고 (메모리 부족 위험)
- 힙 메모리 사용률이 85% 이하이면 → 정상
- 메트릭 데이터를 가져올 수 없으면 → 데이터 없음

### 의미
힙 메모리 사용률이 높아지면 가비지 컬렉션(GC)이 자주 발생하여 애플리케이션의 응답 시간이 느려집니다. 85%를 초과하면 GC가 거의 지속적으로 실행되어 서비스가 거의 멈춘 것처럼 느려질 수 있습니다. 90%를 초과하면 OutOfMemoryError가 발생할 위험이 매우 높습니다.

## 체크 6: 로그 기반 에러 발생 체크

### 제목
최근 5분간 에러 발생 (Error Rate from Logs)

### 목적
최근 5분간 발생한 에러의 빈도를 확인하여 서비스에 문제가 발생하고 있는지, 또는 에러율이 증가하고 있는지 확인합니다.

### 계산
Docker 로그에서 최근 5분간의 로그를 가져와서 "error", "exception", "failed" 문자열이 포함된 줄을 검색합니다. 대소문자 구분 없이 검색하며, 매칭된 줄의 개수를 세어 에러 발생 건수를 계산합니다.

### 판단
- 최근 5분간 에러 발생 건수가 10건을 초과하면 → 경고 (에러 발생 빈도가 높음)
- 최근 5분간 에러 발생 건수가 10건 이하이면 → 정상
- 에러가 10건 이상이면 최근 에러 샘플 5개를 함께 표시

### 의미
에러 발생 빈도가 높아지면 서비스에 문제가 발생하고 있거나, 트래픽이 증가하여 자연스럽게 에러가 증가하고 있을 수 있습니다. 특히 정상 운영 시에는 거의 에러가 발생하지 않아야 하므로, 갑자기 에러가 증가하면 문제 원인을 즉시 파악해야 합니다. 에러 샘플을 통해 어떤 종류의 에러가 발생하는지 확인할 수 있습니다.

## 체크 7: 최근 로그 요약

### 제목
최근 로그 요약 (Recent Log Summary)

### 목적
서비스의 최근 활동을 확인하여 어떤 작업이 수행되고 있는지, 정상적인 패턴인지 확인합니다.

### 계산
Docker 로그에서 최근 20줄을 가져온 후, 그 중 마지막 10줄만 표시합니다.

### 판단
- 특별한 판단 기준 없음 (정보 제공 목적)
- 로그 내용을 보고 수동으로 이상 여부 판단

### 의미
최근 로그를 통해 서비스가 어떤 작업을 수행하고 있는지, 정상적인 요청이 처리되고 있는지, 또는 비정상적인 패턴이 있는지 확인할 수 있습니다. 다른 체크 항목들과 함께 보면 문제의 원인을 파악하는 데 도움이 됩니다. 예를 들어, 에러율이 높은데 로그에서 특정 패턴이 반복되면 그 패턴이 문제의 원인일 수 있습니다.
