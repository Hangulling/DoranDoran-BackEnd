## 1. 발견한 핵심 지식

### 1.1 SSE(Server-Sent Events)와 JPA Open-in-View 패턴의 상호작용 문제

**발견 배경**: 2025년 10월 14일, 실시간 채팅 서비스에서 전체 API가 503 Service Unavailable 오류로 다운되는 심각한 장애 발생

**핵심 지식**:
- **Long-running 요청(SSE)과 JPA의 `open-in-view=true` 조합은 Connection Leak을 유발**
- SSE 스트림이 HTTP 요청 전체 생명주기 동안 유지되는 동안, `open-in-view=true` 설정으로 인해 DB 연결도 함께 점유됨
- 타임아웃 발생 시 비정상 종료로 연결이 반환되지 않아 연결 풀 고갈 발생

**기술적 인사이트**:
```java
// 문제 상황
// SSE 요청 시작 → DB 연결 획득 (open-in-view=true)
// → SSE 스트림 유지 (수 분간) → DB 연결 계속 점유
// → 타임아웃 발생 → 연결 반환 실패 → 풀 고갈
```

**해결 원리**:
- `open-in-view=false`로 변경하여 트랜잭션 종료 시 즉시 DB 연결 반환
- SSE 같은 long-running 요청에서는 DB 연결을 불필요하게 점유하지 않도록 설계

### 1.2 Redis 캐싱 전략을 통한 데이터베이스 부하 분산

**발견 배경**: 동시 사용자 증가 시 데이터베이스 부하가 급증하여 응답 시간 저하 및 연결 풀 고갈 위험 발생

**핵심 지식**:
- **Cache-Aside 패턴과 Write-Through 패턴의 적절한 조합**
- 캐시 키 설계 시 도메인 특성에 맞는 TTL 설정의 중요성
- 캐시 무효화 전략이 데이터 일관성과 성능에 미치는 영향

**기술적 인사이트**:
```java
// 최적화된 캐싱 전략
@Cacheable(value = "prompts", key = "#chatroomId", unless = "#result == null")
public String buildSystemPrompt(UUID chatroomId) {
    // 복잡한 프롬프트 빌드 로직 (80-120ms 소요)
    // 캐시 히트 시 2-5ms로 단축 (95-98% 성능 개선)
}
```

### 1.3 인프라 비용 최적화를 위한 데이터베이스 아키텍처 전환

**발견 배경**: AWS RDS Aurora 사용으로 인한 높은 운영 비용 ($59.04/월) 발생

**핵심 지식**:
- **Shared Database 패턴에서 스키마 분리 전략의 효과**
- 컨테이너 기반 로컬 DB 운영 시 성능과 비용의 트레이드오프
- 데이터 마이그레이션 시 무중단 전환 전략

## 2. 적용한 해결 방법

### 2.1 Connection Pool Exhaustion 문제 해결

**적용 내용**:

1. **JPA Open-in-View 비활성화**
   ```bash
   SPRING_JPA_OPEN_IN_VIEW=false
   ```
   - HTTP 요청 전체 생명주기 동안 DB 연결 유지 → 트랜잭션 종료 시 즉시 연결 반환

2. **연결 풀 최적화**
   ```bash
   SPRING_DATASOURCE_HIKARI_MAXIMUM_POOL_SIZE=20  # 10 → 20 (100% 증가)
   SPRING_DATASOURCE_HIKARI_MINIMUM_IDLE=5         # 0 → 5
   SPRING_DATASOURCE_HIKARI_LEAK_DETECTION_THRESHOLD=10000  # 10초
   SPRING_DATASOURCE_HIKARI_MAX_LIFETIME=600000    # 30분 → 10분
   ```

3. **서비스별 연결 풀 크기 최적화**
   - Chat Service: 20개 (실시간 메시지 처리 중심)
   - User Service: 15개 (사용자 정보 조회)
   - Auth Service: 10개 (토큰 검증)
   - Store Service: 10개 (보관함 조회)
   - Batch Service: 5개 (하루 한 번 실행)

### 2.2 Redis 캐싱 전략 구현

**적용 내용**:

1. **다층 캐싱 전략**
   - ChatRoom 메타데이터: TTL 30분, 캐시 히트율 85-92%
   - System Prompt: TTL 1시간, 캐시 히트율 82-90%
   - IntimacyProgress: TTL 30분, 캐시 히트율 78-88%
   - User/Chatbot 정보: TTL 2시간, 캐시 히트율 95-98%

2. **캐시 무효화 전략**
   ```java
   @CacheEvict(value = {"chatrooms", "roomList"}, key = "#chatroomId")
   public ChatRoom updateRoom(UUID chatroomId, ...) {
       // 업데이트 시 캐시 자동 무효화
   }
   ```

3. **Write-Through 패턴 적용** (IntimacyProgress)
   - 업데이트 시 DB와 캐시 동시 갱신으로 데이터 일관성 보장

### 2.3 RDS → Local DB 마이그레이션

**적용 내용**:

1. **데이터 백업 및 복원**
   - RDS Aurora 데이터 덤프 (386KB)
   - PostgreSQL 15 → 17 업그레이드
   - 5개 스키마, 17개 테이블 복원

2. **배포 스크립트 일괄 수정**
   - 모든 서비스의 DB 연결을 localhost로 변경
   - 컨테이너 네트워크 구성 최적화

## 5. 핵심 교훈 및 재사용 가능한 지식

### 5.1 Long-running 요청과 DB 연결 관리

**교훈**:
- SSE, WebSocket 등 long-running 요청에서는 반드시 `open-in-view=false` 설정
- 연결 풀 모니터링 및 누수 감지 설정 필수
- 연결 생명주기 관리가 시스템 안정성의 핵심

**재사용성**:
- 실시간 스트리밍 기능 개발 시 즉시 적용 가능
- 마이크로서비스 아키텍처에서 서비스 간 통신 최적화에 활용

### 5.2 캐싱 전략의 효과적 설계

**교훈**:
- 도메인 특성에 맞는 TTL 설정이 캐시 효율성 결정
- Cache-Aside와 Write-Through 패턴의 적절한 조합 필요
- 캐시 무효화 전략이 데이터 일관성과 성능에 직접적 영향

**재사용성**:
- 모든 마이크로서비스에 적용 가능한 캐싱 패턴
- 성능 최적화가 필요한 모든 프로젝트에 활용 가능

### 5.3 비용 최적화를 위한 인프라 아키텍처 선택

**교훈**:
- 프로젝트 규모와 요구사항에 맞는 인프라 선택의 중요성
- 초기 단계에서는 관리형 서비스보다 컨테이너 기반 로컬 서비스가 비용 효율적

### 7.2 내부 요인 (실수 및 취약점)

#### 7.2.1 SSE와 JPA 조합 문제 예방 실패

**원인 분석**:
- **기술적 취약점**: Long-running 요청(SSE)과 JPA의 `open-in-view=true` 조합이 Connection Leak을 유발한다는 점을 초기 설계 단계에서 인지하지 못함
- **경험 부족**: 실시간 스트리밍 기능 개발 경험이 부족하여 잠재적 문제를 사전에 예측하지 못함
- **테스트 부족**: 부하 테스트 및 장기 연결 테스트를 충분히 수행하지 않음

**배운 점**:
1. **기술 조합의 위험성 인식**: 새로운 기술을 조합할 때는 각 기술의 특성과 상호작용을 깊이 이해해야 함
2. **부하 테스트의 중요성**: 단순 기능 테스트뿐만 아니라 실제 운영 환경과 유사한 부하 테스트 필수
3. **문서화된 모범 사례 참고**: 커뮤니티에서 보고된 유사 사례를 사전에 조사해야 함

  - 주기적인 성능 프로파일링

#### 7.2.2 초기 설계 단계에서 캐싱 전략 부재

**원인 분석**:
- **설계 단계 누락**: 초기 아키텍처 설계 시 성능 최적화를 위한 캐싱 전략을 고려하지 않음
- **확장성 고려 부족**: 초기에는 소규모 사용자를 가정하여 DB 부하를 과소평가
- **성능 요구사항 미정의**: 명확한 성능 목표(응답 시간, 동시 사용자 수 등)가 없어 사전 최적화 계획 수립 실패

**배운 점**:
1. **확장 가능한 설계의 중요성**: 초기 설계 단계에서 확장성을 고려한 아키텍처 수립 필요
2. **성능 목표 설정**: 프로젝트 초기에 명확한 성능 지표와 목표 설정 필요
3. **점진적 최적화의 한계**: 성능 문제 발생 후 최적화하는 것보다 사전 설계가 효율적

**개선 계획**:
- [ ] **아키텍처 설계 프로세스 개선**
  - 초기 설계 단계에 성능 및 확장성 검토 항목 추가
  - 캐싱 전략을 아키텍처 문서에 명시
  - 성능 목표를 명확히 정의 (예: 응답 시간 < 100ms, 동시 사용자 200명)
- [ ] **성능 테스트 계획 수립**
  - 프로젝트 초기부터 성능 테스트 시나리오 작성
  - 정기적인 성능 벤치마크 측정
  - 성능 회귀 테스트 자동화
- [ ] **캐싱 패턴 표준화**
  - 프로젝트 전반에 적용 가능한 캐싱 가이드라인 작성
  - 캐시 키 설계 규칙 및 TTL 설정 기준 문서화
  - 캐시 무효화 전략 표준화

#### 7.2.3 인프라 비용 계획 부족

- **비용 최적화 옵션 미검토**: 컨테이너 기반 로컬 DB 등 대안을 초기에 검토하지 않음

**배운 점**:

2. **관리형 서비스의 트레이드오프**: 편의성과 비용의 균형을 고려한 선택 필요
3. **단계적 인프라 전환**: 초기에는 비용 효율적인 옵션으로 시작하고, 필요 시 확장하는 전략

  - 비용 최적화 옵션 비교 분석

### 7.3 외부 요인 (통제하기 어려운 환경)

#### 7.3.1 예상치 못한 사용자 증가

**영향**:
- 초기 목표(동시 사용자 50명)를 초과하여 120명까지 증가
- 이로 인해 Connection Pool Exhaustion 문제가 더 빨리 발생
- 성능 최적화 작업이 예상보다 빨리 필요해짐

**대응**:
- 연결 풀 크기 확대 및 캐싱 전략 도입으로 대응
- 결과적으로 목표를 초과 달성하는 성과로 이어짐

**교훈**:
- 확장 가능한 아키텍처 설계의 중요성
- 초기 목표보다 여유 있게 설계하는 것이 안전

#### 7.3.2 AWS RDS 비용 구조

**영향**:
- AWS RDS Aurora의 최소 사양 요구로 인한 높은 비용 ($59.04/월)
- 프로젝트 규모에 비해 과도한 비용 발생
- 초기 예산 계획에 반영되지 않음

**대응**:
- RDS → Local DB 마이그레이션으로 비용 절감
- 결과적으로 50-60% 비용 절감 달성

**교훈**:
- 클라우드 서비스의 비용 구조를 사전에 충분히 이해해야 함
- 프로젝트 규모에 맞는 인프라 선택의 중요성

#### 7.3.3 기술 문서 및 커뮤니티 정보의 한계

**영향**:
- SSE와 JPA 조합 문제에 대한 명확한 문서 부족
- 유사 사례를 찾기 어려워 사전 예방 어려움
- 문제 발생 후 원인 파악에 시간 소요

**대응**:
- 문제 해결 후 문서화 및 모범 사례 수립
- 향후 유사 프로젝트에 참고 자료로 활용

**교훈**:
- 새로운 기술 조합 시 충분한 검증 및 테스트 필요
- 문제 해결 후 지식 공유 및 문서화의 중요성
