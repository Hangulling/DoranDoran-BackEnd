### 2. 응답 시간 체크 ✅

**결과**: 정상 (임계값 1.2초 미만)

**엔드포인트별 상세**:
```
/api/auth/login: 평균 0.140초 (요청 수: 67건)
/api/auth/me: 평균 0.021초 (요청 수: 63건)

전체 평균 응답 시간: 0.082초 (총 요청 수: 130건, 엔드포인트: 2개)
```

**분석**:
- ✅ 두 엔드포인트 모두 1.2초 미만으로 정상 범위
- `/api/auth/login`이 상대적으로 느리지만 정상 범위 (0.140초)
- `/api/auth/me`는 매우 빠름 (0.021초) - 우수한 성능
- 전체 평균 0.082초는 매우 우수한 수준

**의미**: 
- 응답 시간이 급증하지 않았고, 병목 현상이 발생하지 않았습니다.
- 평소보다 3배 이상 느려지지 않았으므로 심각한 병목은 없습니다.

**권장사항**: 
- 트래픽이 증가해도 현재 응답 시간을 유지할 수 있도록 모니터링 지속

### 3. 데이터베이스 연결 풀 체크 ✅

**결과**: 정상 (사용률 0%)

**상세**:

활성 연결: 0.0 / 최대: 30.0 (사용률: 0%)
대기 중인 연결 요청: 없음

**분석**:

- 대기 중인 연결 요청 없음
- 연결 풀 포화 위험 없음

**의미**: 
- 데이터베이스 연결이 충분히 여유 있어서 병목 현상이 발생하지 않습니다.
- 최대 30개 연결 중 0개만 사용 중이므로 여유가 많습니다.

**권장사항**: 
- 트래픽이 증가해도 연결 풀은 충분히 버틸 수 있을 것으로 예상
- 사용률이 90%를 초과하면 경고 필요

### 4. Circuit Breaker 상태 ✅

**결과**: ✅ 정상 (CLOSED 상태)

**상세**:
- Circuit Breaker 상태: CLOSED (0)
- 하위 서비스(User)와의 통신 정상

**의미**: 
- Circuit Breaker가 OPEN 상태가 아니므로 하위 서비스(User)에 장애가 없습니다.
- 실패율이 임계값(70%)을 초과하지 않았습니다.

**참고**: 
- Circuit Breaker가 OPEN 상태가 되면 하위 서비스로의 요청이 즉시 차단되어 실패 응답을 반환합니다.
- 현재는 CLOSED 상태이므로 모든 요청이 정상적으로 하위 서비스로 전달됩니다.

---

### 5. 힙 메모리 사용률 ✅

**결과**: 정상 (사용률 16%)

**상세**:
```
힙 메모리: 159.38MB / 957.99MB (사용률: 16.00%)
```

**분석**:
- 힙 메모리 사용률이 16%로 매우 여유 있음
- 85% 임계값보다 훨씬 낮음
- OutOfMemoryError 위험 없음

**의미**: 
- 가비지 컬렉션(GC)이 자주 발생하지 않아서 애플리케이션 성능에 영향을 주지 않습니다.
- 메모리 부족으로 인한 성능 저하 위험이 없습니다.

**권장사항**: 
- 사용률이 85%를 초과하면 경고
- 90%를 초과하면 OutOfMemoryError 위험이 매우 높아짐

---

### 6. 에러 발생 ⚠️

**결과**: ⚠️ 경고 (24건, 임계값 10건 초과)

**상세**:
- 최근 5분간 에러 발생 건수: 24건
- 임계값: 10건 (초과)

**주요 에러 패턴**:
```
User Service 호출 실패 - getUserByEmailForAuth: 
email=test18@dorandran.test, 
error=[404] during [GET] to [http://dorandoran-user:8082/api/users/auth/email/...]
java.lang.RuntimeException: User Service를 사용할 수 없습니다. 잠시 후 다시 시도해주세요.
```

**분석**:
- 대부분의 에러는 존재하지 않는 이메일로 인한 404 에러
- User Service가 정상 작동 중이지만, 존재하지 않는 사용자 조회 시도로 인한 정상적인 실패 케이스
- Circuit Breaker가 CLOSED 상태이므로 하위 서비스 장애는 아님
- 실제 서비스 장애가 아니라 비즈니스 로직상 정상적인 실패 케이스

**의미**: 
- 실제 장애는 아니지만, 로그 볼륨이 증가할 수 있습니다.
- 존재하지 않는 사용자 조회 시도가 많아서 에러 로그가 증가하고 있습니다.

**권장사항**: 
1. **에러 로깅 완화 고려**: 존재하지 않는 사용자 조회는 정상적인 실패 케이스이므로 로그 레벨을 WARN 또는 INFO로 조정
2. **에러 분석**: 404 에러가 많다면 회원가입 플로우나 이메일 검증 로직 점검
3. **모니터링 지속**: 실제 장애와 구분하기 위해 주기적 모니터링 필요

---

### 7. 최근 로그 요약
