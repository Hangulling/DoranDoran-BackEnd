# Admin 스키마 설계 문서

**작성일**: 2026-01-14  
**목적**: Admin 기능을 위한 데이터베이스 스키마 설계 및 구현 계획

## 1. 작성 배경 및 이유

### 1.1 작성 배경
- Koach Admin(어드민) 시스템 구축을 위한 데이터베이스 스키마 설계 필요
- MVP 단계에서 관리자 기능 제공을 위한 핵심 테이블 구조 정의
- 서버 DB와 로컬 DB 간 동기화 누락으로 인한 문제 해결 필요

### 1.2 작성 이유
1. **관리자 인증/인가 시스템**: Admin 사용자 계정 관리 및 역할 기반 접근 제어
2. **채팅 내역 관리**: 사용자 채팅 로그 조회 및 관리 기능
3. **관리 필요 내역 처리**: 문제가 있는 대화를 티켓으로 관리
4. **프롬프트 관리**: 프롬프트 버전 관리 및 배포 기능
5. **감사 로그**: 모든 관리자 작업 이력 추적

## 2. 구현 지시받은 기능

### 2.1 사용자 채팅 내역 조회
- **기능**: 사용자 채팅 내역 리스트/상세 조회
- **API**: 
  - `GET /admin/meta/chat-rooms` - 채팅룸 옵션 조회
  - `GET /admin/meta/intimacy-levels` - 친밀도 옵션 조회
  - `GET /admin/conversations` - 대화 목록 조회 (필터링: dateFrom, dateTo, roomKey, intimacyLevel, userEmail)
  - `GET /admin/conversations/{conversationId}` - 대화 상세 조회

### 2.2 관리 필요 내역 관리
- **기능**: "관리 필요 내역"으로 내보내기(티켓 생성) 및 처리
- **API**:
  - `POST /admin/review-tickets` - 티켓 생성
  - `GET /admin/review-tickets` - 티켓 목록 조회 (필터: status, agentType, page, size)
  - `GET /admin/review-tickets/{ticketId}` - 티켓 상세 조회
  - `PUT /admin/review-tickets/{ticketId}` - 티켓 수정
  - `DELETE /admin/review-tickets/{ticketId}` - 티켓 삭제
  - `POST /admin/review-tickets/{ticketId}/done` - 티켓 완료 처리

### 2.3 프롬프트 관리
- **기능**: 프롬프트 테스트/편집/저장/적용(Active 반영) 및 버전 관리
- **API**:
  - `GET /admin/prompts/active` - 활성 프롬프트 조회
  - `POST /admin/prompts/test` - 프롬프트 테스트
  - `POST /admin/prompts/versions` - 새 버전 생성
  - `GET /admin/prompts/versions` - 버전 목록 조회
  - `GET /admin/prompts/versions/{versionId}` - 버전 조회
  - `POST /admin/prompts/activate` - 프롬프트 활성화

### 2.4 관리 이력(감사 로그)
- **기능**: 모든 관리자 작업 이력 조회
- **API**:
  - `GET /admin/audit-logs` - 감사 로그 조회 (필터: from, to, actionType, adminId, page, size)

## 3. 데이터베이스 스키마 설계

### 3.1 스키마 위치
모든 Admin 관련 테이블은 **`user_schema`**에 위치합니다.

### 3.2 테이블 설계

#### 3.2.1 admin_users (관리자 사용자)
```sql
CREATE TABLE user_schema.admin_users (
    id BIGINT PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY,
    username VARCHAR(255) NOT NULL UNIQUE,
    password_hash VARCHAR(255) NOT NULL,
    name VARCHAR(255) NOT NULL,
    is_active BOOLEAN NOT NULL DEFAULT true,
    created_at TIMESTAMP NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMP NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_admin_users_username ON user_schema.admin_users(username);
CREATE INDEX idx_admin_users_is_active ON user_schema.admin_users(is_active);
```

**설명**:
- 관리자 계정 정보 저장
- username은 유니크 제약조건
- is_active로 계정 활성화/비활성화 관리

#### 3.2.2 admin_roles (관리자 역할)
```sql
CREATE TABLE user_schema.admin_roles (
    id BIGINT PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY,
    role_name VARCHAR(50) NOT NULL UNIQUE,
    description VARCHAR(255),
    created_at TIMESTAMP NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_admin_roles_role_name ON user_schema.admin_roles(role_name);
```

**역할 종류** (MVP):
- `VIEWER`: 조회만 가능
- `REVIEWER`: 관리 필요 내역 처리
- `PROMPT_MANAGER`: 프롬프트 편집/적용/배포
- `SUPER_ADMIN`: 관리자/권한 관리 (향후 확장)

#### 3.2.3 admin_user_roles (관리자-역할 매핑)
```sql
CREATE TABLE user_schema.admin_user_roles (
    admin_user_id BIGINT NOT NULL,
    admin_role_id BIGINT NOT NULL,
    created_at TIMESTAMP NOT NULL DEFAULT NOW(),
    PRIMARY KEY (admin_user_id, admin_role_id),
    CONSTRAINT fk_admin_user_roles_user 
        FOREIGN KEY (admin_user_id) 
        REFERENCES user_schema.admin_users(id) 
        ON DELETE CASCADE,
    CONSTRAINT fk_admin_user_roles_role 
        FOREIGN KEY (admin_role_id) 
        REFERENCES user_schema.admin_roles(id) 
        ON DELETE CASCADE
);

CREATE INDEX idx_admin_user_roles_user ON user_schema.admin_user_roles(admin_user_id);
CREATE INDEX idx_admin_user_roles_role ON user_schema.admin_user_roles(admin_role_id);
```

**설명**:
- 관리자와 역할의 다대다 관계
- 한 관리자는 여러 역할 보유 가능
- CASCADE 삭제로 데이터 무결성 보장

#### 3.2.4 review_tickets (관리 필요 내역 티켓)
```sql
CREATE TABLE user_schema.review_tickets (
    id BIGINT PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY,
    conversation_id UUID,
    status VARCHAR(20) NOT NULL DEFAULT 'OPEN',
    agent_type VARCHAR(50),
    note TEXT,
    created_by UUID,
    assignee UUID,
    created_at TIMESTAMP NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMP NOT NULL DEFAULT NOW(),
    done_at TIMESTAMP,
    CONSTRAINT chk_review_tickets_status 
        CHECK (status IN ('OPEN', 'DONE'))
);

CREATE INDEX idx_review_tickets_status ON user_schema.review_tickets(status);
CREATE INDEX idx_review_tickets_agent_type ON user_schema.review_tickets(agent_type);
CREATE INDEX idx_review_tickets_created_at ON user_schema.review_tickets(created_at);
CREATE INDEX idx_review_tickets_conversation ON user_schema.review_tickets(conversation_id);
CREATE INDEX idx_review_tickets_assignee ON user_schema.review_tickets(assignee);
```

**설명**:
- 관리자가 검토해야 할 대화를 티켓으로 관리
- status: OPEN(미처리), DONE(처리완료)
- agent_type: 탭 분류용 (intimacy/conver/voca)
- conversation_id: 채팅 대화 ID 참조

#### 3.2.5 review_ticket_items (관리 필요 내역 상세 항목)
```sql
CREATE TABLE user_schema.review_ticket_items (
    id BIGINT PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY,
    ticket_id BIGINT NOT NULL,
    message_id BIGINT NOT NULL,
    agent_type VARCHAR(50) NOT NULL,
    snapshot_json JSONB,
    created_at TIMESTAMP NOT NULL DEFAULT NOW(),
    CONSTRAINT fk_review_ticket_items_ticket
        FOREIGN KEY (ticket_id)
        REFERENCES user_schema.review_tickets(id)
        ON DELETE CASCADE
);

CREATE INDEX idx_review_ticket_items_ticket ON user_schema.review_ticket_items(ticket_id);
CREATE INDEX idx_review_ticket_items_msg_agent ON user_schema.review_ticket_items(message_id, agent_type);
```

**설명**:
- 티켓 생성 시 선택된 user/intimacy/conver/voca 항목을 저장
- snapshot_json으로 당시 상태 보존

#### 3.2.6 admin_audit_logs (관리 감사 로그)
```sql
CREATE TABLE user_schema.admin_audit_logs (
    id BIGINT PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY,
    admin_user_id UUID NOT NULL,
    action_type VARCHAR(50) NOT NULL,
    target_type VARCHAR(50),
    target_id BIGINT,
    summary VARCHAR(500),
    before_json JSONB,
    after_json JSONB,
    ip VARCHAR(50),
    user_agent VARCHAR(500),
    created_at TIMESTAMP NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_admin_audit_logs_admin_user ON user_schema.admin_audit_logs(admin_user_id);
CREATE INDEX idx_admin_audit_logs_action_type ON user_schema.admin_audit_logs(action_type);
CREATE INDEX idx_admin_audit_logs_created_at ON user_schema.admin_audit_logs(created_at);
CREATE INDEX idx_admin_audit_logs_target ON user_schema.admin_audit_logs(target_type, target_id);
```

**action_type 예시**:
- `ACTIVATE`: 프롬프트 활성화
- `CREATE`: 생성
- `UPDATE`: 수정
- `DELETE`: 삭제
- `TEST`: 테스트

**target_type 예시**:
- `PROMPT`: 프롬프트
- `REVIEW_TICKET`: 리뷰 티켓
- `CONVERSATION`: 대화

**설명**:
- 모든 관리자 작업 이력 추적
- before_json, after_json으로 변경 전후 상태 저장
- IP, User-Agent로 보안 감사 지원

## 4. 기존 테이블과의 관계

### 4.1 프롬프트 관련 테이블 (문서 기준 존재, 서버 DDL 미확인)
- `user_schema.prompt_versions`: 프롬프트 버전 관리
- `user_schema.prompt_actives`: 활성 프롬프트 관리
- 서버 DDL 덤프 기준으로는 두 테이블이 존재하지 않으므로 실제 구축 여부 확인 필요
- Docker DB의 `dorandoran`/`postgres` DB 모두에서 미존재 확인됨

### 4.2 채팅 관련 테이블 (참조)
- `chat_schema.messages`: 채팅 메시지
- `chat_schema.chatrooms`: 채팅방
- `chat_schema.agent_results`: 에이전트 결과

## 6. 보안 고려사항

### 6.1 인증/인가
- 모든 `/admin/**` API는 Admin Access Token 필요
- 역할 기반 접근 제어 (RBAC) 구현
- JWT 토큰에 역할 정보 포함

### 6.2 감사 로그
- 모든 관리자 작업은 반드시 감사 로그 기록
- 민감한 정보 변경 시 before_json, after_json 저장
- IP, User-Agent 추적으로 보안 감사 지원
