**작성일**: 2026-01-14  
**목적**: 구현 지시받은 기능 분석 및 스키마 구현 계획

## 1. 구현 지시받은 기능 분석

### 1.1 사용자 채팅 내역 조회
**기능 요구사항**:
- 채팅룸 옵션 조회 (Friend 등)
- 친밀도 옵션 조회 (1, 2, 3)
- 대화 목록 조회 (날짜, 채팅룸, 친밀도, 사용자 이메일 필터링)
- 대화 상세 조회 (타임라인 형태)

**필요한 데이터**:
- 채팅방 정보 (chat_schema.chatrooms)
- 메시지 정보 (chat_schema.messages)
- 에이전트 결과 (chat_schema.agent_results)
- 사용자 정보 (user_schema.app_user)

**스키마 영향**: 기존 테이블 활용, 추가 스키마 불필요

---

### 1.2 관리 필요 내역 관리
**기능 요구사항**:
- 대화 상세에서 "관리 필요 내역"으로 내보내기 (티켓 생성)
- 티켓 목록 조회 (상태: OPEN/DONE, 에이전트 타입 필터)
- 티켓 카운트 조회 (에이전트 타입별)
- 티켓 메모 수정
- 티켓 삭제
- 티켓 처리 완료 (다건 가능)

**필요한 데이터**:
- 티켓 정보 (conversation_id, status, agent_type, note)
- 티켓 생성자 (created_by)
- 티켓 담당자 (assignee)
- 티켓 아이템 (message_id, agent_type, snapshot_json)
- 생성/수정/완료 시간

**스키마 영향**: 
- ✅ `review_tickets` 테이블 필요
- ✅ `review_ticket_items` 테이블 필요 (문서 명세에 있음)

---

### 1.3 프롬프트 관리

- 활성 프롬프트 조회 (env, agentType 기준)

- 새 버전 생성 (저장)
- 버전 목록 조회

**필요한 데이터**:
- 프롬프트 버전 정보 (agent_type, version, content, memo)
- 활성 프롬프트 정보 (env, agent_type, prompt_version_id)
- 생성자 정보 (created_by_admin_id)
- 활성화 정보 (activated_by_admin_id, activated_at)

**스키마 영향**: 
- ✅ `prompt_versions` 테이블 (이미 존재)
- ✅ `prompt_actives` 테이블 (이미 존재)
- ⚠️ `created_by_admin_id`, `activated_by_admin_id` 컬럼 필요 (현재 UUID로 되어있을 수 있음)

## 2. 스키마 구현 계획

### 2.1 테이블 생성 우선순위

#### Phase 1: 관리자 인증/인가 (최우선)
**이유**: 모든 Admin 기능의 기반이 되는 인증/인가 시스템

1. **admin_users** 테이블
   - 관리자 계정 정보 저장
   - 로그인 기능에 필수

2. **admin_roles** 테이블
   - 역할 정의
   - 초기 데이터 삽입 필요

3. **admin_user_roles** 테이블
   - 관리자-역할 매핑
   - 역할 기반 접근 제어에 필수

#### Phase 2: 관리 필요 내역 (High Priority)
**이유**: 핵심 비즈니스 기능

4. **review_tickets** 테이블
   - 티켓 정보 저장
   - created_by, assignee는 UUID (admin_users와의 관계는 추후 확장 가능)

5. **review_ticket_items** 테이블 (문서 명세 확인 필요)
   - 티켓 아이템 정보
   - snapshot_json으로 당시 상태 보존

#### Phase 3: 감사 로그 (High Priority)
**이유**: 보안 및 감사 요구사항

6. **admin_audit_logs** 테이블
   - 모든 관리자 작업 이력
   - admin_user_id는 UUID (현재 엔티티 기준)

#### Phase 4: 프롬프트 관리 (Medium Priority)
**이유**: 기존 테이블 수정 필요

7. **prompt_versions** 테이블 수정
   - `created_by_admin_id` 컬럼 추가 (BIGINT, FK to admin_users)
   - 현재 UUID인 경우 마이그레이션 필요

8. **prompt_actives** 테이블 수정
   - `activated_by_admin_id` 컬럼 추가 (BIGINT, FK to admin_users)
   - 현재 UUID인 경우 마이그레이션 필요

### 2.2 상세 스키마 설계

#### 2.2.1 admin_users
```sql
CREATE TABLE user_schema.admin_users (
    id BIGINT PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY,
    username VARCHAR(255) NOT NULL UNIQUE,
    password_hash VARCHAR(255) NOT NULL,
    name VARCHAR(255) NOT NULL,
    is_active BOOLEAN NOT NULL DEFAULT true,
    created_at TIMESTAMP NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMP NOT NULL DEFAULT NOW()
);
```

**인덱스**:
- `idx_admin_users_username` (UNIQUE)
- `idx_admin_users_is_active`

**초기 데이터**: 없음 (수동 생성)

---

#### 2.2.2 admin_roles
```sql
CREATE TABLE user_schema.admin_roles (
    id BIGINT PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY,
    role_name VARCHAR(50) NOT NULL UNIQUE,
    description VARCHAR(255),
    created_at TIMESTAMP NOT NULL DEFAULT NOW()
);
```

**인덱스**:
- `idx_admin_roles_role_name` (UNIQUE)

**초기 데이터**:
```sql
INSERT INTO user_schema.admin_roles (role_name, description) VALUES
('VIEWER', '조회만 가능한 역할'),
('REVIEWER', '관리 필요 내역 처리 역할'),

('SUPER_ADMIN', '모든 권한을 가진 관리자 역할');
```

---

#### 2.2.3 admin_user_roles
```sql
CREATE TABLE user_schema.admin_user_roles (
    admin_user_id BIGINT NOT NULL,
    admin_role_id BIGINT NOT NULL,
    created_at TIMESTAMP NOT NULL DEFAULT NOW(),
    PRIMARY KEY (admin_user_id, admin_role_id),
    CONSTRAINT fk_admin_user_roles_user 
        FOREIGN KEY (admin_user_id) 
        REFERENCES user_schema.admin_users(id) 
        ON DELETE CASCADE,
    CONSTRAINT fk_admin_user_roles_role 
        FOREIGN KEY (admin_role_id) 
        REFERENCES user_schema.admin_roles(id) 
        ON DELETE CASCADE
);
```

**인덱스**:
- `idx_admin_user_roles_user` (admin_user_id)
- `idx_admin_user_roles_role` (admin_role_id)

---

#### 2.2.4 review_tickets
```sql
CREATE TABLE user_schema.review_tickets (
    id BIGINT PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY,
    conversation_id UUID,
    status VARCHAR(20) NOT NULL DEFAULT 'OPEN',
    agent_type VARCHAR(50),
    note TEXT,
    created_by UUID,
    assignee UUID,
    created_at TIMESTAMP NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMP NOT NULL DEFAULT NOW(),
    done_at TIMESTAMP,
    CONSTRAINT chk_review_tickets_status 
        CHECK (status IN ('OPEN', 'DONE'))
);
```

**인덱스**:
- `idx_review_tickets_status` (status)
- `idx_review_tickets_agent_type` (agent_type)
- `idx_review_tickets_created_at` (created_at DESC)
- `idx_review_tickets_status_created` (status, created_at) -- 문서 명세
- `idx_review_tickets_agent_status_created` (agent_type, status, created_at) -- 문서 명세
- `idx_review_tickets_conversation` (conversation_id)
- `idx_review_tickets_assignee` (assignee)

**참고**: 
- `created_by`, `assignee`는 현재 UUID로 설계 (엔티티 기준)
- 향후 admin_users와 연결하려면 BIGINT로 변경 필요

---

#### 2.2.5 review_ticket_items (문서 명세 확인)
```sql
CREATE TABLE user_schema.review_ticket_items (

    created_at TIMESTAMP NOT NULL DEFAULT NOW(),
```

**인덱스**:

## 4. 주의사항 및 고려사항

### 4.1 데이터 타입 불일치
**문제**: 
- `admin_audit_logs.admin_user_id`는 UUID
- `review_tickets.created_by`, `assignee`는 UUID
- `admin_users.id`는 BIGINT

**해결 방안**:
1. **Option A**: admin_users.id를 UUID로 변경 (기존 엔티티와 일치)
2. **Option B**: admin_audit_logs, review_tickets의 UUID 컬럼을 BIGINT로 변경하고 FK 추가
3. **Option C**: 현재 상태 유지 (FK 없이 UUID로만 참조)

**권장**: Option B (데이터 무결성 확보)

## 6.1 서버 DB DDL 확인 결과 (2026-01-17)

서버 Docker의 PostgreSQL(`dorandoran`)에서 `user_schema`, `chat_schema`, `archive_schema`를 덤프해 확인한 결과는 다음과 같다.

- **admin/review/prompt 테이블 없음**: `admin_users`, `admin_roles`, `admin_user_roles`, `review_tickets`, `review_ticket_items`, `admin_audit_logs`, `prompt_versions`, `prompt_actives`가 모두 **미존재**
- **user_schema**: `app_user`, `profiles`, `settings`만 존재
- **archive_schema**: `arch_chatrooms`, `arch_messages`, `arch_agent_results`, `arch_ingestion_state`, `arch_intimacy_progress`, `arch_stores`, `arch_usage_events` 등 **확장 구조로 존재**
- **chat_schema**: 메시지/채팅방/친밀도 등 운영 테이블 정상 존재
- **추가 확인**: `prompt_versions`, `prompt_actives`는 `dorandoran`/`postgres` DB 어디에도 **미존재**

따라서 admin 기능 관련 스키마는 **서버 기준으로도 신규 생성 대상**이며, prompt 테이블 역시 **서버에 미구축** 상태로 판단된다.

## 7. 개발 체크리스트 대비 점검

아래는 제공된 개발 체크리스트와 본 문서의 범위를 비교한 점검 결과이다. 본 문서는 **스키마/백엔드 엔티티 중심**이므로 UI/프론트엔드 항목은 범위 외로 분류했다.

### A. 어드민 공통 레이아웃/인증

- 어드민 로그인/세션(JWT) 및 로그아웃: **부분 포함** (admin_users/admin_roles/admin_user_roles 스키마만 계획, 인증 흐름/세션 로직은 미포함)
- 좌측 메뉴 라우팅 + 선택 상태 표시: **범위 외**
- 권한 분리(조회/편집/배포): **부분 포함** (roles 스키마만 계획, 실제 권한 체크 로직은 미포함)
- 공통 로딩/에러/빈화면: **범위 외**
- 공통 페이징 컴포넌트: **범위 외**

### B. 채팅 로그 조회

#### 1) 사용자 채팅 내역(리스트)

- 날짜 필터 입력/유효성: **범위 외** (프론트/UI/검증 로직)
- 채팅룸/친밀도 옵션 로딩: **부분 포함** (필요 데이터는 기존 테이블 활용 언급)
- 조회하기(검색 API): **범위 외**
- 결과 테이블 렌더링/상세 이동: **범위 외**
- 페이지네이션: **범위 외**

#### 2) 사용자 채팅 상세(타임라인)

- 메시지/에이전트 결과 시간순 표시: **부분 포함** (필요 데이터만 명시)
- 타입별 UI/스크롤/말줄임: **범위 외**
- 선택 체크박스/내보내기 버튼: **부분 포함** (review_tickets/review_ticket_items 스키마 계획)

#### 3) 내보내기 모달(등록)

- 항목 선택 UI/메모 입력/등록/취소: **범위 외**
- 등록 성공 시 큐 생성: **부분 포함** (review_tickets/review_ticket_items 스키마 계획)

### C. 관리 필요 내역(운영 큐)

- 타입 탭/카운트/상태 탭/리스트/체크박스/페이지네이션: **범위 외**
- 수정/삭제/처리완료: **부분 포함** (review_tickets 스키마에 status, note, done_at 포함)

### D. 프롬프트 운영

#### 1) 프롬프트 테스트 및 적용

- 에이전트 선택/테스트/편집/저장/롤백/연동 리스트/페이지네이션: **범위 외**
- 저장/적용 이력/권한 연동: **부분 포함** (prompt_versions/prompt_actives에 admin 참조 컬럼 추가 계획)

#### 2) 프롬프트 버전 관리

- 버전 리스트/배포/조회/롤백: **범위 외**
- 버전 메타(작성자 등): **부분 포함** (created_by_admin_id/activated_by_admin_id 계획)

### E. 히스토리(감사 로그)

- 관리 이력 조회/페이지네이션/필터/상세(diff): **부분 포함**
  - admin_audit_logs 스키마 및 인덱스 계획 포함
  - 조회 API/필터/화면 설계는 미포함

### Archive 스키마(관리자용 채팅 로그/감사 기록)

- 제공된 Archive 스키마 정의: **범위 외**
  - 본 문서는 `user_schema` 내 admin 기능용 스키마에 집중
  - archive_schema는 별도 문서/마이그레이션으로 분리 필요

### 보완 필요 목록(스키마 관점)

1. **review_ticket_items 엔티티/레포지토리**: 계획에는 있으나 구현 상세/연계 로직 명시 필요
2. **admin_users와 UUID 컬럼 불일치**: Option B 권장으로 문서화되어 있으나 실제 마이그레이션/변경 범위 확정 필요
3. **prompt_* 테이블의 기존 UUID 컬럼 처리 전략**: NULL 허용 방안 외에 데이터 이행 계획 필요
4. **서버 DDL 기준 prompt/admin/review 테이블 미존재**: 서버 생성 계획 및 배포 순서 확정 필요
